# Конституция проекта «Интеграция bsp + uf_demo»

Рабочая область `Q:\integration` объединяет два подпроекта — конфигурации 1С `bsp/` (БСП 3.1.12.348, формат выгрузки 2.20) и `uf_demo/` («ДемонстрационноеПриложение» 1.0.41.3, формат выгрузки 2.21) — с целью настройки обмена между ними (Kafka через внешнюю компоненту librdkafka, расширения СШП/ЭТШ/ИТШ). Конституция задаёт принципы (MUST/SHOULD), обязательные для всех фич; детальные правила — в `AGENTS.md` корня и подпроектов.

## Core Principles

### I. Разработка только в расширениях (Extension-First)

Вся функциональная разработка ведётся в расширениях `src/extensions/<ИмяРасширения>/` соответствующего подпроекта. Основная конфигурация (`src/Configuration.xml`, каталоги объектов) не изменяется без явного указания пользователя. Новые объекты именуются с префиксом `NamePrefix` своего расширения (`СШП_`, `ЭТШ_`, `ИТШ_`, `ВТ_`, `КОЛ_`, `КД_`); заимствованные — без префикса, с UUID основной конфигурации (`ObjectBelonging = Adopted`). UUID в XML не изменяются; состав объектов метаданных (добавление/удаление файлов объектов) меняется только через Конфигуратор с последующей выгрузкой в файлы.

Rationale: расширения отделяют кастомизацию от вендорских конфигураций, сохраняя возможность штатного обновления и переносимость наработок.

### II. Совместимость и самодостаточность расширений

Режим совместимости расширения (`ConfigurationExtensionCompatibilityMode`) не выше режима совместимости основной конфигурации: для `bsp` ≤ 8.3.24, для `uf_demo` ≤ 8.3.27. Расширение самодостаточно: оно не вызывает общие модули других расширений (перекрёстные ссылки ломают изолированный синтаксический контроль; мелкие хелперы — локальные копии), клиентский код форм сообщает через `Сообщить()`. Файлы выгрузки: UTF-8 с BOM, переводы строк CRLF; буква «ё» в именах метаданных (`Name`) запрещена (в `Synonym` допустима).

Rationale: изолированная компилируемость (`/CheckConfig` компилирует расширение отдельно) и корректная загрузка Конфигуратором — условия независимой поставки расширений.

### III. Приёмка через Vanessa-сценарии (BDD)

Каждая сквозная функция покрывается Vanessa-сценариями до объявления готовности: проверки модулей (сервер), работа форм, сквозные сценарии. После загрузки расширения в базу запускается синтаксический контроль: применимость + модули в контекстах ThinClient/Server/ExternalConnection + целостность конфигурации (`db-cfe-admin check`). Тестовые базы: `bsp` — `C:\Users\sax\Documents\InfoBase22` (автоматическое применение расширений к ней разрешено), `uf_demo` — `C:\Users\sax\Documents\uf-demo-test` (применение — по явной команде).

Rationale: приёмочные сценарии — объективное доказательство работоспособности; без них «готовность» не декларируется.

### IV. Минимально достаточное решение (SOLID, DRY, KISS)

Один модуль/процедура — одна ответственность; общая логика не дублируется, а выносится в переиспользуемые функции; решение минимально достаточно, без избыточных абстракций и кода «на будущее» (YAGNI). Существующие модули не изменяются: новый код — в новых модулях/процедурах; правки существующих (общих, объектных, модулей форм) — только по явному указанию пользователя.

Rationale: вендорские конфигурации обновляются штатно; минимум правок чужого кода — минимум конфликтов при обновлении и при изолированной компиляции расширений.

### V. Безопасность данных и среды (NON-NEGOTIABLE)

Запрещено при любых операциях:

- завершать сеансы пользователей — никогда, даже для операций, требующих монопольного режима (блокировка → сообщить и ждать решения пользователя);
- автоматически применять расширения к рабочим базам — только по явной команде (исключение: тестовая `InfoBase22`);
- редактировать `ConfigDumpInfo.xml` вручную (его ведёт Конфигуратор) и изменять UUID в XML;
- изменять бинарные файлы выгрузок (`*.bin`, картинки `CommonPictures/`);
- передавать кириллицу в аргументы `1cv8`/`V8.com` из cmd — значения зашиваются в `.ps1`-файлы (UTF-8 с BOM).

Rationale: перечисленные действия необратимы или приводят к потере данных; решение о риске принимает только пользователь.

## Технические ограничения и стандарты

- **Платформы**: `bsp` — 8.3, совместимость 8.3.24; `uf_demo` — 1С:Предприятие 8.5, совместимость 8.3.27, расширения 8.5.1. Форматы выгрузки: 2.20 (`bsp`), 2.21 (`uf_demo`).
- **Стиль кода**: BSL — по стандартам v8std (ИТС) через скилл `bsl-code-standards`; запросы — через скилл `bsl-queries` с проверкой индексов по XML-выгрузке.
- **Инструкция проекта**: иерархия `AGENTS.md` — корневой файл + файлы подпроектов; при работе внутри подкаталога его `AGENTS.md` обязателен и приоритетнее корневых общих правил. Конституция задаёт принципы; `AGENTS.md` — детальные правила и конвенции.
- **Расширения с внешними компонентами** (СШП, ЭТШ, ИТШ): после первой загрузки в информационную базу снять «Безопасный режим» и «Защиту от опасных действий» (только GUI Конфигуратора; `ibcmd` отсутствует).
- **Kafka-обмен**: только через расширения СШП/ЭТШ/ИТШ и внешнюю компоненту librdkafka из общих макетов; новые обмены наследуют их паттерны (порции, ручной коммит при порции без ошибок).

## Процесс разработки

- **SDD-поток**: `$speckit-specify` → (опционально `$speckit-clarify`) → `$speckit-plan` → `$speckit-tasks` → (опционально `$speckit-analyze`) → `$speckit-implement` → (опционально `$speckit-converge`). Артефакты фичи — в `specs/<NNN>-<имя>/`; текущая фича фиксируется в `.specify/feature.json`.
- **Перед `$speckit-implement`** — проверка соответствия плана и задач принципам I–V; несоответствия устраняются до начала кода.
- **Проверка модулей расширения** запускается сразу после загрузки расширения в базу (принцип III).
- **Git**: единый репозиторий в корне `Q:\integration` (ветка `main`); пуш и создание репозиториев — только по явной команде пользователя.
- **Коммуникация**: ответы — на русском; кратко, без воды и повторов; при веб-поиске — раздел «Sources:» с markdown-ссылками.

## Governance

- Конституция приоритетнее остальных практик и артефактов проекта. При противоречии конституции и `AGENTS.md`: конституция задаёт принципы (MUST-правила разделов Core Principles и Безопасности), `AGENTS.md` — детальные конвенции; выявленное противоречие устраняется поправкой соответствующего файла.
- **Поправки** — только через `$speckit-constitution`, с Sync Impact Report (HTML-комментарий в начале файла, удаляется перед коммитом) и семантическим версионированием: MAJOR — удаление/переопределение принципа или несовместимое изменение правил; MINOR — новый принцип/секция или существенное расширение; PATCH — уточнения формулировок без изменения смысла. Даты — ISO `YYYY-MM-DD`.
- **Compliance**: каждая фича при `$speckit-implement` и при приёмке проверяется на соответствие принципам I–V; нарушение принципа V останавливает работу до решения пользователя.

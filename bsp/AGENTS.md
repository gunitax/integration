# AGENTS.md

Руководство для ИИ-агентов и разработчиков, работающих с этим репозиторием.

## Что это за проект

XML-выгрузка конфигурации «Демонстрационная конфигурация "Библиотека стандартных подсистем", редакция 3.1» (БСП 3.1):
- Поставщик: Фирма «1С», версия 3.1.12.348.
- Формат: выгрузка Конфигуратора («Сохранить конфигурацию в файлы»), версия формата 2.20. Это НЕ проект 1C:EDT — структура папок иная.
- Платформа: режим совместимости 8.3.24, управляемое приложение, режим обычного приложения не используется.
- Вариант встроенного языка: **русский**. Все имена метаданных, переменных и код — на русском.
- Лицензия кода: CC BY 4.0 (заголовок в каждом .bsl-файле).

Масштаб: 3139 файлов .bsl, ~1,33 млн строк кода; 826 общих модулей, 109 справочников, 199 регистров сведений, 155 обработок, 166 ролей, 69 регламентных заданий, 52 отчёта, 25 документов, 16 подсистем, 121 общая форма, 70 пакетов XDTO, 13 веб-сервисов, 4 HTTP-сервиса.

## Структура репозитория

Выгрузка конфигурации лежит в каталоге `src/` — метаданные разложены по разделам:

- `src/Configuration.xml` — корневой объект конфигурации (свойства, роли по умолчанию, интерфейсы).
- `src/ConfigDumpInfo.xml` — служебный файл соответствия версий объектов выгрузки. Генерируется Конфигуратором.
- `src/extensions/` — выгрузки расширений конфигурации, по одной папке на расширение (см. раздел «Доработки и расширения»). Основная конфигурация её не использует.
- `src/Ext/` — модули приложения: `SessionModule.bsl` (модуль сеанса), `ManagedApplicationModule.bsl` (управляемое приложение), `ExternalConnectionModule.bsl`, `OrdinaryApplicationModule.bsl`, интерфейсы, заставка.
- Разделы метаданных (папки во множественном числе): `Catalogs` (справочники), `Documents` (документы), `InformationRegisters` (регистры сведений), `AccumulationRegisters` (регистры накопления), `AccountingRegisters` (регистры бухгалтерии), `CommonModules` (общие модули), `CommonForms`, `CommonCommands`, `Enums`, `Subsystems`, `Roles`, `Reports`, `DataProcessors` (обработки), `ScheduledJobs`, `ExchangePlans`, `WebServices`, `HTTPServices`, `XDTOPackages` и т.д.

Внутри каждого раздела на один объект метаданных приходится пара «файл + папка»:

```
src/Documents/
  _ДемоЗаказПокупателя.xml        <- описание метаданных объекта (реквизиты, табличные части, движения)
  _ДемоЗаказПокупателя/
    Ext/
      ObjectModule.bsl            <- модуль объекта
      ManagerModule.bsl           <- модуль менеджера
      Help.xml, Help/ru.html
    Forms/
      ФормаДокумента.xml          <- описание формы
      ФормаДокумента/Ext/Form.xml <- макет формы (элементы)
      ФормаДокумента/Ext/Form/Module.bsl <- модуль формы
    Templates/                    <- макеты
```

Имена файлов модулей: `Module.bsl` (общий модуль), `ObjectModule.bsl`, `ManagerModule.bsl`, `Form/Module.bsl` (форма), `Template.xml` (макет), `Command/Module.bsl` (команда).

Объекты демонстрационной конфигурации имеют префикс `_Демо` (например, `_ДемоЗаказПокупателя`). Подсистемы: `СтандартныеПодсистемы`, `Администрирование`, `ТехнологияСервиса` и `_Демо*` для демонстрационных разделов.

## Критические правила работы с файлами

1. **Кодировка и переводы строк.** Все текстовые файлы — UTF-8 **с BOM**, переводы строк **CRLF**. При правках сохраняйте и то, и другое: без BOM Конфигуратор не загрузит файл, смешение переводов строк ломает diff и повторную выгрузку.
2. **UUID не трогать.** `uuid` в XML идентифицирует объект метаданных в информационной базе. Смена UUID = потеря данных при обновлении.
3. **`ConfigDumpInfo.xml` не редактировать руками.** Он управляется Конфигуратором при сохранении/загрузке выгрузки. После правок через Конфигуратор он обновится сам; ручные правки почти всегда приводят к полному перезаливанию конфигурации.
4. **Структуру XML не реорганизовывать.** Порядок элементов и отступы (табуляция) значимы для повторной загрузки и читаемости diff. Правки — точечные, в существующих узлах.
5. **Бинарные файлы** (`ParentConfigurations.bin`, `StandaloneConfigurationContent.bin`, картинки в `CommonPictures/`) не редактировать.
6. Изменение состава объектов (добавление/удаление файла объекта) без обновления `Configuration.xml` и `ConfigDumpInfo.xml` сломает загрузку — состав объектов меняется только через Конфигуратор.

## Соглашения по коду (стиль БСП)

Суффиксы общих модулей задают контекст вызова — при создании новых модулей следуйте той же схеме:

| Суффикс | Контекст |
|---|---|
| — (без суффикса) | сервер, серверные вызовы |
| `Клиент` | только клиент (клиент-серверный модуль) |
| `КлиентСервер` | клиент + сервер без контекстных вызовов |
| `ВызовСервера` | клиентский модуль для обращения к серверу |
| `ПовтИсп` | повторное использование возвращаемых значений |
| `Переопределяемый` | модуль, переопределяемый в конфигурации-потребителе |
| `Служебный` | внутренние процедуры БСП, не для прикладного использования |
| `Глобальный` | точка входа (в свойствах модуля) |

Прочие соглашения:
- Заголовок лицензии CC BY 4.0 в начале каждого модуля — сохранять.
- Области кода: `#Область ПрограммныйИнтерфейс` (экспортные), `#Область СлужебныеПроцедурыИФункции`, `#Область ОбработчикиСобытий` — соблюдать порядок.
- Экспортные процедуры/функции помечаются `Экспорт` и снабжаются doc-комментарием с разделом `Параметры:` (типы через `-` на отдельных строках).
- Запросы — на языке запросов 1С, конкатенация строк запроса через `<<КодЗапроса>>` в типовых процедурах БСП не используется; текст запроса — строковый литерал.
- Имена: `КэмелКейс` на русском, без подчёркиваний (кроме префикса `_Демо`).

## Доработки и расширения

**Все доработки конфигурации выполняются в расширениях (если явно не указано иное).** Основная конфигурация — поставляемая БСП, её не изменять.

- Расширения хранятся в `src/extensions/<ИмяРасширения>/` — каждая папка является самостоятельной выгрузкой расширения (свой `Configuration.xml` и `ConfigDumpInfo.xml`).
- Эталоны формата — поставляемые демо-расширения: `src/extensions/_ДемоПустоеРасширение/` (минимальный состав) и `src/extensions/_ДемоРасширение/` (все виды объектов, заимствования, формы, роли). Новые расширения создавать по их образцу.
- Новые объекты — собственные для расширения (без `ObjectBelonging` в `Properties`); заимствованные — с `ObjectBelonging = Adopted` первым свойством и UUID основной конфигурации.
- Назначение расширения — «Дополнение» (`AddOn`) для новых объектов, «Адаптация» (`Customization`) для правки форм/модулей основной конфигурации.
- Режим совместимости расширения (`ConfigurationExtensionCompatibilityMode`) должен быть **не выше** режима совместимости основной конфигурации (`CompatibilityMode`, здесь 8.3.24). Режим выше — расширение не подключается («Режим совместимости расширения больше режима совместимости основной конфигурации»).
- Обязательный состав расширения: заимствованный язык (`Languages/Русский.xml`, `ObjectBelonging = Adopted`, запись `<Language>Русский</Language>` в `ChildObjects` корня) — без него синонимы `v8:lang = ru` не разрешаются и загрузка зависает; а также `xr:PropertyState` (CommandInterface, MainSectionCommandInterface = Extended) в `InternalInfo` корня. `DefaultRoles` в расширениях этой поставки не используется.

## Сборка и проверка

Это выгрузка, а не собираемый проект — «сборки» в привычном смысле нет. Жизненный цикл изменений:

- **Загрузка в Конфигуратор**: Конфигуратор → «Загрузить конфигурацию из файлов» → каталог `src/`. Обратная операция — «Сохранить конфигурацию в файлы» (обновляет `ConfigDumpInfo.xml`).
- **Расширения**: Конфигуратор → Конфигурация → «Расширения конфигурации» → «Добавить» → «Загрузить из файлов» → папка расширения в `src/extensions/`. Обратно — «Выгрузить в файлы» в ту же папку.
- **Проверка расширений загрузкой в базу.** Реализацию расширения проверять сразу загрузкой в тестовую информационную базу `File="D:\infobase\infobase22"` (пользователь `Администратор`, пароль пустой) — пакетным запуском платформы (`/LoadConfigFromFiles <папка> -Extension <Имя>`, при необходимости `/UpdateDBCfg`) или через Конфигуратор. Это штатная часть цикла правки расширения, отдельного разрешения не требует.
- **Проверка синтаксиса**: в Конфигураторе «Проверка конфигурации» (Ctrl+F7 в конфигураторе после загрузки); автономной CLI-проверки BSL в репозитории нет.
- **Запуск**: демо-конфигурация запускается в режиме управляемого приложения платформы 8.3.27+.

Текстовые правки (код, строки интерфейса) допустимы прямо в файлах выгрузки; структурные изменения состава метаданных делаются в Конфигураторе с последующим сохранением выгрузки обратно в репозиторий.

## Vanessa Automation

Сценарные (BDD) проверки через Vanessa Automation 1.2.043.42 — каталог `Vanessa/` (перенесён из стенда хакатона, см. `Vanessa/README.md` и `Vanessa/ИНСТРУКЦИЯ-ПЕРЕНОС.md`).

- **Прогон**: `powershell -NoProfile -ExecutionPolicy Bypass -File Vanessa\smoke-infobase22.ps1` (smoke на тестовой базе InfoBase22) или напрямую `Vanessa\va.ps1 -Feature <файл.feature> -BasePath D:\infobase\infobase22 -User Администратор -PreLaunchClient`. Файлы сценариев — `Vanessa/features/`; приёмочные сценарии ПКО — `Vanessa/features/kassa/`.
- **Успех**: `status.txt` в отчёте равен `0`, в `junit.xml` есть хотя бы один сценарий и нет `failure/error/skipped`; код выхода процесса сам по себе успехом не считается. Отчёты — `Vanessa/reports/run-<дата-время>/` (junit.xml, steps.log, manager.log, screenshots), в git не коммитятся.
- **Расширение `VAExtension` 1.32** должно быть загружено и применено в базе (штатно сделано в InfoBase22; повторная установка — `powershell -NoProfile -ExecutionPolicy Bypass -File Vanessa\install\install-va-infobase22.ps1`). Без него шаги с внешней компонентой VanessaExt не работают.
- **Особенность машины**: `WshShell.Run` здесь не запускает bat-файлы («Не удается дождаться процесса»), поэтому штатный запуск тест-клиента из Vanessa падает. Раннер обходит это ключом `-PreLaunchClient`: va.ps1 сам запускает тест-клиент (тонкий клиент 8.5.1.1529), Vanessa подключается к нему по TCP (`ИмяКомпьютера` = 127.0.0.2, порт из `-ClientPort`). Без этого ключа поведение штатное (для машин, где bat работает).
- Кириллицу в аргументы 1cv8 из cmd передавать нельзя — значения зашивать в .ps1-файлы (UTF-8 с BOM), как сделано в `Vanessa/*.ps1`.

## Запрещённые действия

При работе с информационной базой и Конфигуратором:

- **Никогда не завершать сеансы пользователей.** Даже если операция требует монопольного режима (обновление конфигурации базы данных, загрузка конфигурации из файлов) — не завершайте активные сеансы и не принуждайте базу к монопольному режиму. Если операция блокируется работающими пользователями — сообщите об этом и дождитесь явного решения пользователя.
- **Не применять расширения к рабочим базам автоматически.** Применение расширения к информационной базе (загрузка расширения, «Обновить конфигурацию базы данных», установка режима безопасного режима и защиты от опасных действий) выполняется только по явной команде пользователя. Без команды — только подготовка и правка файлов расширения в `src/extensions/`. Исключение — тестовая база `File="D:\infobase\infobase22"` (Администратор, пароль пустой): загрузка туда расширений для проверки разрешена штатно (см. «Сборка и проверка»).

# XML расширения

Основной источник правил схемы XML и заимствования. Образцы в [samples](samples)
задают состав узлов; имена, типы и UUID исходных объектов брать из `1c/config`.
Подключение и совместимость — [stand.json](../../../stand.json).
Команды загрузки и ошибки раннера — [справочник стенда](../onec-development/references/setup.md#extension-lifecycle).

<a id="format"></a>
## Формат файлов

Для этого стенда писать `version="2.20"` и не копировать `Caption` / `ShortCaption`.
Формат 2.21 и эти свойства были отвергнуты установленной платформой при загрузке
расширения. Это правило файлов расширения: выгрузку типовой не преобразовывать массово
и не загружать вместо расширения. Сохранять порядок узлов схемы.

У значений перечислений, скопированных из выгрузки 2.21, удалять свойство `Color`.
При загрузке в формате 2.20 установленная платформа сообщает: «Свойство Color
не входит в состав объекта метаданных EnumValue». Имя, синоним и UUID значения
перечисления сохранять в обычном порядке. Узел `StandardAttributes` не копировать в свойства перечисления, справочника,
документа и регистра сведений: в выгрузке 2.20 нового объекта его нет.
У табличной части документа он остаётся, сразу после `FillChecking`, и за ним
идёт `LineNumberLength` со значением 9. У табличной части справочника вместо
`StandardAttributes` стоит `Use`, затем тот же `LineNumberLength`. У реквизита
табличной части нет `FillFromFillingValue` и `FillValue`: после `MaxValue` сразу
`FillChecking`.

UTF-8 BOM не ставить на каждый XML. У уже загруженного расширения
`ТренировкаЗакупок` метка `EF BB BF` есть только у `ConfigDumpInfo.xml`.
Пустой лог Конфигуратора этой меткой не лечится: см.
[отказы загрузки](../onec-development/references/setup.md#runner-load).

Узел `Use` табличной части содержит значение перечисления (`ForItem`),
а не вложенные `xr:Common` / `xr:Attributes`. Неправильное `Use` не даёт
ошибки: импорт зависает с пустым журналом, рабочий набор Конфигуратора
растёт до десятков гигабайт. Замена на `ForItem` возвращает обычные
диагностики платформы (исправлено и подтверждено 21.10.2026, отчёт —
`docs/reports/approval-repair-20261021.md`).

В формате 2.20 платформа отвергает и свойства из выгрузки 2.21, которых
у нового объекта нет: `UseInInterfaceCompatibilityMode` у общей формы,
`AuxiliaryVariantForm` у отчёта. Не переносить их из типовых образцов.

<a id="external-epf"></a>
## EPF: сборка успешна, но основной реквизит формы стал строкой

Симптом: при открытии EPF вызов `РеквизитФормыВЗначение("Объект")` падает с
«Недопустимое значение параметра (параметр номер '1')», хотя форма копии в расширении
работает. На 8.3.27.2325 это воспроизведено при совпадении UUID корневого
`ExternalDataProcessor` и `InternalInfo/xr:ContainedObject/xr:ObjectId`.

1. Проверить эти два UUID в корневом XML. При совпадении заменить внутренний
   `xr:ObjectId` новым UUID, сохранив UUID корня и остальные идентификаторы.
   `xr:ClassId` не менять. При создании новой обработки сразу давать разные UUID.
2. Пересобрать EPF и выполнить `dump-external` в новый каталог внутри `1c/tmp`;
   точные команды — [справочник](../onec-development/references/setup.md#commands).
3. В выгруженном `Forms/<Форма>/Ext/Form.xml` проверить основной реквизит:
   `MainAttribute=true`, тип `cfg:ExternalDataProcessorObject.<ИмяОбработки>`.
   `xs:string` вместо него означает, что дефект остался; исправление одного исходного
   `Form.xml` без устранения совпадения UUID не подтверждает исправность EPF.
4. Открыть пересобранный EPF в свежем клиенте и проверить пользовательский путь по
   [методике внешних обработок](../onec-development/references/checks.md#external-epf).

Если UUID уже различаются, не менять их наугад: сравнить обратную выгрузку с
исходниками и диагностировать фактически потерянный тип. Этот обход не объясняет
все возможные причины ошибки параметра.

<a id="presentation"></a>
## Представления и события формы

`ObjectPresentation` и `ListPresentation` — это строка локализации, как
`ListPresentation` в `Documents/УчебныйЗаказНаЗакупку.xml`. Внутри сразу
`v8:item`, без обёртки `Synonym`:

```xml
<ObjectPresentation>
  <v8:item>
    <v8:lang>ru</v8:lang>
    <v8:content>Документ сервиса</v8:content>
  </v8:item>
</ObjectPresentation>
```

Обёртка `<ObjectPresentation><Synonym><v8:item>…` даёт при загрузке:
«Ошибка XDTO … при чтении свойства: Synonym» и «НачалоСвойства: ObjectPresentation …
Тип: LocalStringType». То же для `ListPresentation`. Синоним самого объекта
метаданных по-прежнему записывается как `Synonym` с `v8:item`.

`Title` управляемой формы — тоже `LocalStringType`, образец —
`DataProcessors/Удвоение/Forms/Форма/Ext/Form.xml`. Внутри сразу `v8:item`.
Обёртка `<Title><Synonym><v8:item>…` на кнопке, странице, реквизите или команде
формы даёт «НачалоСвойства: Title … LocalStringType» и следом
«НачалоСвойства: … Synonym». Это не синоним объекта метаданных.

У поля управляемой формы узел `Events` ставить после `ExtendedTooltip`, как в
выгрузке УТ. Порядок `DataPath`, `Events`, `Title`, `ExtendedTooltip` схема не принимает.

<a id="form-metadata"></a>
## Метаданные формы

Для поля табличного документа имя XML-узла — `SpreadSheetDocumentField`
(образец: `1c/config/DataProcessors/ЗагрузкаТоваровИзВнешнихФайлов/Forms/Форма/Ext/Form.xml`).
Вариант `SpreadsheetDocumentField` был принят загрузкой без сообщения об ошибке,
но поле отсутствовало в интерфейсе Vanessa. Проверять наличие поля и содержимое
после открытия формы; успешная загрузка сама по себе это не подтверждает.

Файл `Forms/<Имя>.xml` описывает объект метаданных `Form`; файл
`Forms/<Имя>/Ext/Form.xml` — содержимое управляемой формы. Образец брать для
соответствующего файла и вида объекта, а не переносить свойства обработки или константы.

В `Form/Properties` не добавлять `ExtendedPresentation`, даже пустой:
платформа отвергает его с диагностикой «Свойство ExtendedPresentation не входит
в состав объекта метаданных Form». При таком отказе удалить узел именно у `Form`.
У констант и обработки одноимённое свойство допустимо; массово удалять его по
всему расширению нельзя. Это подтверждено при чтении XML `Автосервиса`:
ошибки были в метаданных формы настроек и формы документа сервиса.

Реквизит динамического списка описывать типом `cfg:DynamicList` с `MainAttribute=true`
и `MainTable`; для простого списка справочника использовать штатный запрос основной
таблицы, а не произвольный. Значения и порядок узлов настроек (`DefaultCommand`,
`SearchStringLocation`, `ListSettings`) брать из выгрузки формы того же вида:
посторонние группы вроде `dataControl` и порядок «по памяти» загрузка отвергает.

Формы, назначенные основными у объекта (`DefaultObjectForm`, `DefaultListForm` и
другие), включать в `ChildObjects` владельца и указывать полными ссылками
метаданных (`Catalog.<Имя>.Form.<Форма>`), а не коротким именем формы.
Обработчики, перечисленные в XML подписок на события, должны существовать,
быть экспортными и совпадать по параметрам с событием; пропуски показывает
только полная проверка конфигурации с `handlersExistence`.

<a id="attribute-names"></a>
## Имена собственных реквизитов

Не создавать в справочнике собственный реквизит `Владелец`: это имя стандартного
реквизита. Платформа сообщает «Справочник.ТранспортныеСредства — Недопустимое
имя реквизита — Владелец». Для владельца автомобиля использовать отдельное
техническое имя, например `ВладелецАвтомобиля`, сохранив синоним «Владелец».
Имена других новых реквизитов также сверять со стандартными реквизитами данного
вида объекта по справке платформы и проверенному образцу.

При переименовании собственного реквизита сохранить его UUID и обновить
`ConfigDumpInfo.xml`, обращения в BSL и запросах, пути данных форм и ссылки в правах,
если они есть. Различать объекты при замене: стандартный `АвтоРабочиеУчастки.Владелец`
для подчинения станции обслуживания оставить без изменений; заимствованные
реквизиты типовой также не переименовывать.

## Имена новых объектов и сохранность UUID

До создания собственного объекта искать имя в `1c/config` и в исходниках других
подключённых расширений. Имя уникально в пределах вида метаданных: собственный
справочник с именем типового справочника не превращается в заимствованный объект.
Для новых объектов выбирать отличительное русское техническое имя, сохраняя
удобный пользовательский синоним. `ТранспортныеСредства` и `РабочиеУчастки`
уже есть в УТ этого стенда; собственные справочники Автосервиса названы
`АвтоТранспортныеСредства` и `АвтоРабочиеУчастки`.

При переименовании собственного объекта сохранить UUID объекта, реквизитов и
табличных частей; переименовать файл и каталог модуля. Обновить `Name`,
`xr:GeneratedType/@name`, корневой `ChildObjects`, имена в `ConfigDumpInfo.xml`,
типы и ссылки XML, права, состав подсистемы, BSL и тексты запросов.
Заменять точные имена объекта, не части других идентификаторов и не синонимы.
Копирование образца для нового объекта требует новых UUID и TypeId/ValueId;
исправление существующего объекта требует сохранения его идентификаторов.

## Новое расширение

- `Configuration.xml` — по образцу [АвтоАртикул](samples/АвтоАртикул/Configuration.xml):
  новые `uuid` конфигурации и все `xr:ObjectId` в `InternalInfo` (`xr:ClassId` не трогать),
  своё `Name` и синоним, `ConfigurationExtensionCompatibilityMode` — из stand.json.
  В `ChildObjects` перечислить каждый заимствованный и новый объект.
- `ConfigDumpInfo.xml` дополнять записью на каждый объект, реквизит и модуль, как в образце.

У корневого `Configuration` расширения сохранять `ObjectBelonging=Adopted`,
как в проверенном образце. Сообщение «Загрузка не должна менять принадлежность
основного объекта конфигурации» воспроизводится при загрузке XML расширения
в основную конфигурацию: у `LoadConfigFromFiles` отсутствует `-Extension`.
Исправлять цель загрузки через [харнесс расширений](../onec-development/references/setup.md#extension-lifecycle)
или открывать конфигурацию нужного расширения в Конфигураторе; не заменять
корневую принадлежность на `Own` ради загрузки в типовую.

## Заимствование объекта

Образец — [Catalogs/Номенклатура.xml](samples/АвтоАртикул/Catalogs/Номенклатура.xml).

- Собственный `uuid` объекта; `ObjectBelonging` = `Adopted`; `ExtendedConfigurationObject` —
  `uuid` объекта из `1c/config`.
- `InternalInfo` обязателен: без него загрузка падает с «Internal data (the InternalInfo
  node) is not available». Набор `xr:GeneratedType` (имена и категории) взять из
  исходного объекта в `1c/config`, `TypeId` и `ValueId` — новые.
  Это относится и к заимствованной табличной части: пустой `InternalInfo` отвергается
  платформой. Скопировать её `TabularSection` и `TabularSectionRow` из внутренней
  информации типовой, сохранив имена и категории и заменив идентификаторы типов.
- Каждый реквизит исходного объекта, к которому обращается код расширения, заимствовать
  явно в `ChildObjects`: собственный `uuid`, `Adopted`, `ExtendedConfigurationObject` —
  `uuid` реквизита из `1c/config`, `Type` — копия исходного. Без этого клиент работает,
  а проверка модулей расширения сообщает «Variable is not defined».
- При обращении к менеджеру типового справочника заимствовать и сам объект:
  ссылка `cfg:CatalogRef.Пользователи` в типе реквизита этого не заменяет.
  Для `Справочники.Пользователи.ПустаяСсылка()` extended-проверка выдавала
  «Возможно ошибочное свойство: \"Пользователи\"», хотя серверные тесты проходили.
  После явного заимствования справочника эти диагностики исчезли; проверить
  результат свежей проверкой сервера и клиента.
- При обращении к типовым перечислениям, например
  `Перечисления.СтатусыЗаказовКлиентов.КОбеспечению`, явно заимствовать перечисление
  и используемые значения. Для объекта и каждого значения создать собственный UUID,
  поставить `Adopted` и `ExtendedConfigurationObject` с UUID из `1c/config`.
  Состав `InternalInfo` самого перечисления взять из типовой, TypeId/ValueId заменить
  новыми; у значения использовать пустой `InternalInfo`. Добавить объект в корневой
  `ChildObjects`, объект и значения — в `ConfigDumpInfo.xml`. Импорт может пройти
  без такого заимствования, но extended-проверка модулей сообщает отсутствующее свойство.
  Не добавлять все типы из `cfg:*` автоматически: одной ссылки в типе достаточно
  для импорта; явное заимствование требуется для обращений к объектам из кода.
- Узел `ChildObjects` оставлять и тогда, когда заимствовать реквизиты не нужно, — пустым:
  без него загрузка падает с «unexpected read property … expected property: ChildObjects».
- У заимствованного реквизита перед `Properties` ставить пустой `InternalInfo`, как в
  выгрузке расширения на этой платформе. Пустой `RegisterRecords` в свойствах оставлять
  только у заимствованного документа; у заимствованных справочника и задачи этот узел
  посторонний и загрузке мешает.
- Заимствовать все типовые объекты, к менеджерам и типам которых обращается код
  расширения, а не только те, что видны в типах реквизитов: справочники пользователей
  (`Пользователи`, `ВнешниеПользователи`), регистр исполнителей с его измерениями,
  документы, чьи объекты создаются в тестах. Пропущенные ссылки не видны ни импорту,
  ни зелёным тестам, ни проверке модулей — их показывает полная проверка конфигурации
  (см. [полную проверку](#check-full)).
- Основной язык расширения заимствовать из типовой (например `Language.Русский`,
  сохраняя UUID) и назначать `DefaultLanguage`; без него полная проверка даёт
  диагностики ссылок при пройденном импорте.
- Модуль объекта — `Ext/ObjectModule.bsl` рядом с XML объекта, обработчики с аннотациями
  `&После("ИмяСобытия")` и т. п., как в [образце](samples/АвтоАртикул/Catalogs/Номенклатура/Ext/ObjectModule.bsl).
- Сообщение об отказе из модуля объекта появляется у поля формы, только если указаны
  данные: `ОбщегоНазначенияКлиентСервер.СообщитьПользователю(Текст, ЭтотОбъект, "<Реквизит>",
  "Объект", Отказ)` или `Сообщение.УстановитьДанные(ЭтотОбъект)`. Без этого текст в окне
  сообщений есть, а у поля — нет.

## Типы реквизитов

Проверять ограничения скопированного типа. У `cfg:DefinedType.Цена` в УТ установлен
`AllowedSign=Nonnegative`: отрицательная цена не дошла до собственной проверки.
Если постановка требует явного серверного отказа, собственному числовому реквизиту
задавать `AllowedSign=Any` и проверять значение бизнес-кодом.

## Права новых объектов

У общего модуля расширения оставлять `Privileged=false`: на платформе 8.3.27.2325
значение `true` отвергается при применении с сообщением «Использование привилегированных
общих модулей в расширении недопустимо». Права служебных параметров сеанса проверять
явно; их отложенная инициализация не должна нарушать вход и обычную печать пользователей
без новой роли.

Права роли брать из проверенного `Roles/*/Ext/Rights.xml` для того же вида объекта.
Имена прав сверять с той же выгрузкой, а не строить по памяти: у справочника
неинтерактивное изменение — `Edit` (не `InteractiveUpdate`), удаление —
`InteractiveDelete` (не `InteractiveDeletion`). Права одного объекта
записывать в роли один раз: повторный блок `object` по тому же имени мешает
загрузке. Для перечислений не добавлять объекты `Enum.<Имя>` с правами `Read` / `View`:
таких прав у перечислений нет. Доступ задавать к документу и подсистеме,
как в ролях расширения `ТренировкаЗакупок`.

На этом стенде недопустимые права перечислений в `Автосервисе` приводили
к зависанию импорта с пустым журналом Конфигуратора. В изолированной копии
тот же набор метаданных с такими правами зависал; после удаления записей
`Enum.*` из обеих ролей загрузка завершилась за пять секунд. Проверять роли
до запуска платформы, даже если XML синтаксически корректен.

## Проверка

Перед загрузкой проверить свойства метаданных форм по
[правилу Form](#form-metadata), а собственные имена реквизитов — по
[правилу имён](#attribute-names). Успешный разбор XML и отсутствие повторяющихся
UUID не выявляют эти ошибки: XML может быть корректным, но не приниматься платформой.

Запустить [статическую проверку](scripts/check_xml.py):
`python .agents/skills/onec-extension-xml/scripts/check_xml.py 1c/extensions/<Имя> --base 1c/config`.
Она проверяет формат 2.20, принадлежность корня, найденные ошибки форм и прав,
свойства реквизитов табличной части, `Color` у значений перечислений, собственный
реквизит `Владелец`, UUID, отсутствующие объекты и несовпадающие имена в
`ConfigDumpInfo.xml`, файлы корневого состава, совпадения новых имён с типовой
и UUID явно заимствованных объектов. Проверка имён других расширений и обращений
BSL остаётся отдельной; скрипт не заменяет схему платформы и проверку модулей.
Исправить выявленные отказы перед загрузкой.
При правках XML сохранять все реквизиты и их UUID: в `Автосервисе` восемь
полей табличных частей исчезли из документа, оставаясь в манифесте и путях
данных формы. Для удаления свойства учитывать самозакрывающиеся узлы;
не применять шаблон, который захватывает соседний реквизит.

После структурной проверки выполнить загрузку, проверку модулей и серверные/UI тесты
по [циклу разработки](../onec-development/SKILL.md). Параметры проверки модулей и
диагностика зависимостей YAxUnit — [справочник стенда](../onec-development/references/setup.md#module-check).
Успешный разбор XML сам по себе не подтверждает применимость расширения к базе.

<a id="check-full"></a>
## Полная проверка конфигурации

После зелёных тестов выполнить полную проверку через MCP
`check_syntax_designer_config` с `allExtensions=true`, `handlersExistence=true`,
`incorrectReferences=true`. Она выявляет класс ошибок, который не видят импорт,
проверка модулей и серверные тесты: отсутствующий основной язык, незаемствованные
типовые объекты, используемые из кода, несуществующие обработчики подписок.
На расширении согласования 21.10.2026 зелёный импорт и шесть зелёных тестов
соседствовали с восемью такими диагностика́ми; после заимствования языка,
пользователей и исполнителей полная проверка дала ноль диагностик по расширению
(отчёт — `docs/reports/approval-repair-20261021.md`). Диагностики других
расширений в общей проверке фиксировать отдельно.

Проверенные сценарии применения объектов и границы подтверждения исходников —
в [каталоге примеров](../onec-development/references/examples.md). Выбирать образец того же вида
объекта; старый успешный прогон не отменяет проверку после адаптации.

# Триаж задачи

Основной режим хакатона — **минимальный TDD на YAxUnit → проверенная сборка →
предложение Vanessa**. Пользователь уже выбрал этот порядок: повторно спрашивать
разрешение на YAxUnit в начале каждой задачи не нужно. Явная постановка может
изменить режим, например потребовать UI-приёмку сразу или отказаться от автотестов.

## Быстрый старт

Прочитать постановку и [правила проекта](../../../AGENTS.md), найти только нужные
объекты в `1c/config`. Кратко назвать результат, затронутые метаданные и минимальные
проверки. Триаж — короткое обоснование выбора, а не отдельный этап согласования.
Уточнять только неизвестные требования, без которых нельзя правильно реализовать задачу.
Не читать архив тренировок целиком и не запускать учебную регрессию.

| Поведение задачи | Минимальный тест YAxUnit |
| --- | --- |
| Расчёт, преобразование, валидация | Юнит-тест основного результата и существенного граничного значения/отказа |
| Запись, запрос, связанные объекты, проведение или движения | Интеграционный тест с изолированными данными: действие и повторное чтение результата; критичный отказ при необходимости |
| Форма с бизнес-логикой | Тест выделенной серверной логики; поведение формы оставить для следующего этапа |
| Только оформление, метаданные без проверяемого серверного поведения или документация | Не создавать искусственный тест ради TDD; объяснить исключение и выполнить применимые статические/платформенные проверки |

Для небольшой задачи обычно достаточно 1–3 целевых тестов; это ориентир, не лимит.
Не дублировать одну проверку на нескольких уровнях, не строить общую тестовую
инфраструктуру и не добавлять случаи вне требований. Интеграционный тест нужен,
если юнит-тест не проверит существенное поведение с данными.

## TDD и первая проверенная сборка

Выполнить [цикл разработки](../onec-development/SKILL.md): минимальный каркас
метаданных и вызываемых методов → тест → запуск и ожидаемый красный результат →
реализация → зелёный тест и проверка сборки/модулей. Ошибка загрузки, компиляции
или ноль выполненных тестов не являются красным результатом бизнес-требования.

В `v8project.yaml` включать только текущую задачу и её необходимые зависимости.
YAxUnit ограничивать расширением задачи; его запуск сам выполняет сборку, поэтому
не повторять ту же сборку отдельной командой без причины. Не готовить Vanessa,
UI-фикстуры, поставочные архивы и косметические улучшения до этого результата,
если они прямо не требуются заданием. Форму реализовать в необходимом объёме:
отсрочка её автоматической проверки не разрешает оставлять пользовательский путь незаконченным.

## Предложение Vanessa после реализации

Когда код и необходимая форма готовы, целевая сборка/загрузка успешна, модули
проверены и минимальные тесты зелёные, сообщить фактический результат и число тестов.
Перед вопросом завершить процессы законченного прогона по
[правилам уборки](../onec-development/references/setup.md#run-cleanup); после согласованного UI-прогона
повторить уборку. Подготовка вопроса не требует заранее запускать Vanessa.
Указать, что интерфейс ещё не проверен сценарием. Предложить один короткий путь
Vanessa с конкретными действиями и ожидаемым результатом, затем спросить:
«Реализация и сборка проверены. Прогнать через Vanessa: <путь и результат>?»

До ответа не создавать и не запускать сценарий. При наличии асинхронного вопроса
предложить варианты «Да, целевой сценарий» и «Нет, достаточно текущих проверок».
Молчание не считать согласием. Если Vanessa уже явно запрошена, выполнить её без
повторного согласования. Если у задачи нет UI-пути, объяснить неприменимость Vanessa.
При отказе зафиксировать границу проверки; не заменять её молча долгим ручным прогоном.

После согласия использовать конкретный feature-файл и
[методики UI](../onec-development/references/checks.md#ui). Ошибку реализации
исправить и повторить затронутые проверки. При блокировке сборки или окружения
сообщить блокер и доступные результаты, не объявлять реализацию проверенной.
Команды и известные обходы — [справочник](../onec-development/references/setup.md#commands).

# Развёртывание и отказы харнеса

Это основной справочник команд и проверенных обходов окружения. Правила проекта
и карта остальных источников — [AGENTS.md](../../../../AGENTS.md#где-хранится-знание).
Целевые версии и подключение брать из [stand.json](../../../../stand.json), состав сборки —
из [v8project.yaml](../../../../v8project.yaml), версии и хеши инструментов — из
[v8-runner.json](../../../../scripts/v8-runner.json) и [vanessa.json](../../../../scripts/vanessa.json).
Упомянутые ниже датированные отказы описывают проверенный стенд, а не задают новые версии.

<a id="commands"></a>
## Вход и команды

На Windows использовать `./scripts/onec.ps1`: он выбирает установленный Python,
обходит заглушку WindowsApps и вызывает тот же `scripts/onec.py` с UTF-8.
Полный список параметров — `./scripts/onec.ps1 --help`.

Windows PowerShell 5.1 читает `.ps1` без BOM в системной кодировке. Для
`scripts/onec.ps1` и `scripts/emit-mcp.ps1` сохранять UTF-8 с BOM: иначе русская
строка `throw` может дать `Unexpected token` и ошибку незакрытой кавычки ещё
до запуска Python. При запрете выполнения скриптов можно использовать
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/onec.ps1 doctor`:
политика меняется только для этого процесса, не для системы.

| Задача | Команда |
| --- | --- |
| Готовность стенда и подсказки по отказам | `./scripts/onec.ps1 doctor` |
| Проверка цели и сеансов | `./scripts/onec.ps1 preflight` |
| Предприятие / Конфигуратор | `./scripts/onec.ps1 open` / `./scripts/onec.ps1 designer` |
| Применимость подключённых расширений | `./scripts/onec.ps1 check` |
| Сборка расширений | `./scripts/onec.ps1 v8 build` |
| Сборка внешней обработки из XML | `./scripts/onec.ps1 build-external --path <корневой XML в проекте> --output <EPF в проекте>` |
| Проверка содержимого EPF обратной выгрузкой | `./scripts/onec.ps1 dump-external --path <EPF в проекте> --output <новый корневой XML в проекте>` |
| Серверные тесты со сборкой | `./scripts/onec.ps1 v8 test yaxunit <ИмяРасширения>` |
| Сценарии интерфейса | `./scripts/onec.ps1 va --path 1c/vanessa/features/<Задача>.feature` |
| Запуск / остановка менеджера MCP | `./scripts/onec.ps1 va-mcp` / `./scripts/onec.ps1 va-mcp --stop` |
| Свежий клиент при работающем менеджере | `./scripts/onec.ps1 va-mcp --restart-client` |

Тесты запускать в объёме, выбранном при [триаже](../../onec-task-triage/SKILL.md).
В `v8project.yaml` включать только расширение задачи и необходимые зависимости:
YAxUnit сначала собирает весь этот состав, даже при фильтре одного расширения.
`all` и запуск всего каталога сценариев нужны лишь для явно выбранной общей регрессии.
Учебные сценарии убраны; перед запуском указать существующий feature текущей задачи. `--dry-run` у операций,
которые его поддерживают, показывает команду без выполнения изменения.
`doctor` диагностирует стенд; он может поднять настроенный RAS, если порт свободен,
но не меняет конфигурацию и данные рабочей базы.

<a id="environment"></a>
## Окружение

Этот стенд работает на Windows. Платформа, адреса служб и СУБД заданы в stand.json.
При отсутствии отдельного пользователя СУБД `ibcmd` использует проверку подлинности
Windows текущего пользователя. `onec.py` поднимает RAS на настроенном адресе при
свободном порте. Служба агента сервера должна быть установлена и запущена.

Нужны установленный Python, закреплённый v8-runner и справка платформы
`bin/shcntx_ru.hbk`. MCP `bsl-platform` использует эту справку и Java; `context7` —
официальный HTTP MCP `https://mcp.context7.com/mcp`, заданный в `agent-kit.json`.
Локальный API `context7.com:443` на этом стенде давал таймаут; удалённый MCP
проверен реальным поисковым запросом. Для HTTP Context7 не добавлять `env_vars`: это поле stdio-сервера. Состав и генерация MCP описаны
в [README](../../../../README.md#инструменты-агента); клиентские конфиги вручную не редактировать.

<a id="new-stand"></a>
## Новый стенд

1. Сверить stand.json с установленной платформой и демо-базой. Выполнить `doctor`.
2. Подготовить выгрузку для поиска: если `1c/config` отсутствует, использовать
   `./scripts/onec.ps1 dump-config`. Отсутствие файла выгрузки не доказывает отсутствие
   объекта в базе.
   Для сверки отдельного объекта с установленным релизом использовать отдельный каталог:
   `./scripts/onec.ps1 dump-config --path 1c/tmp/native-reference --objects Catalog.Номенклатура.Form.ФормаСписка`.
   Несколько полных имён передавать отдельными аргументами после `--objects`.
   Корневые объекты могут выгружаться без `ConfigDumpInfo.xml`; харнесс проверяет
   XML каждого запрошенного объекта. Основную выгрузку и замороженную копию не перезаписывать.
3. Подготовить [замороженную копию и кэш основной конфигурации](#frozen-main).
   Это отдельный этап развёртывания, который не повторяют при обычной разработке.
4. Установить YAxUnit из CFE: `./scripts/onec.ps1 v8 tools download yaxunit`.
   Взять полученный файл из `build/tools`, загрузить как `YAXUNIT` по
   [процедуре загрузки](#extension-lifecycle). Исходники `--sources` не использовать:
   они в формате EDT, а каталог `tests/` раннер считает своим. Загрузки инструментов
   находятся в `build/` корня, независимо от `workPath`.
5. Собрать расширения из v8project.yaml и снять [защитные флаги](#flags).
6. Запустить `va`: харнесс скачает закреплённую обработку и создаст отдельную базу-менеджер.
   Для интерактивной работы запустить `va-mcp`, пройти [стартовые окна](#startup-dialogs)
   и подтвердить готовность реальным вызовом инструмента. Для чтения данных установить
   [VAExtension](#va-extension).
7. Выполнить `doctor`, серверные и UI тесты. Сохранить свежие отчёты.

Снимок `.dt` и восстановление относятся к отдельной задаче администрирования.
Если такая задача поставлена, харнесс поддерживает `dump-ib --path <новый файл>` и
`restore-ib --path <снимок> --apply`; существующий файл снимка не перезаписывать.

<a id="extension-lifecycle"></a>
## Загрузка, выгрузка и флаги расширения

Перед изменением проверить `preflight`. При изменении структуры штатно закрыть свой
MCP TestClient через `close_test_client` с профилем «УТ»: открытый клиент уже вызывал
ошибку исключительной блокировки при добавлении справочника. Менеджер в отдельной
базе можно оставить работающим. Зависшие сеансы — [отдельный порядок](#sessions).

```powershell
./scripts/onec.ps1 load-extension --extension <Имя> --path <каталог-XML-или-CFE> --apply
./scripts/onec.ps1 check
```

`load-extension --apply` после успешной загрузки сам снимает безопасный режим и защиту
от опасных действий. Отдельный `unsafe-extension` нужен, только если галки включились
без этой команды: сборка раннера или ручной Конфигуратор.

После загрузки читать свежий лог, затем подключать новый клиент. Для XML харнесс
сверяет имя и совместимость; правила формата — [XML-скилл](../../onec-extension-xml/SKILL.md#format).

Для поставки использовать `export-extension --extension <Имя> --path <новый файл.cfe>`.
Для обратной выгрузки — `dump-extension --extension <Имя> --path <новый каталог>`.
Оба действия вызывать через Windows-вход из [таблицы команд](#commands).
MCP `dump_config` раннера перезаписывает замороженную типовую и ломает сборку.
Проверка именно экспортированного файла и архива — [методика поставки](checks.md#delivery).

<a id="flags"></a>
### Безопасный режим после загрузки

Конфигуратор включает безопасный режим и защиту от опасных действий после первой
и каждой полной перезагрузки расширения. `load-extension --apply` снимает обе галки
сразу после успешного лога. Без этого YAxUnit сообщает, что чтение конфигурационного
файла недоступно, а тест окружения `ТестыУТ` получает «Да» вместо «Нет».
Если галки включились без `load-extension`, снять их той же командой
`unsafe-extension --extension <Имя> --apply`.

Харнесс снимает флаги через форму команды `ibcmd config extension`: форма `extension`
не принимает пользователя ИБ и может бесконечно его переспрашивать. Самостоятельно
вызывать бинарник не нужно. Флаги проверяются `doctor` и серверным тестом окружения.

<a id="sessions"></a>
### Сеанс остался без процесса клиента

После `doctor` и `preflight` закрыть только свой оборванный или явно согласованный сеанс:
`./scripts/onec.ps1 close-session --session <UUID> --apply`.
UUID должен принадлежать целевой базе stand.json; харнесс проверяет это.
Для предварительной проверки есть `--dry-run`. Linux-обёртки `onec-rac` на Windows нет.

<a id="run-cleanup"></a>
## Завершение прогона

После каждого законченного прогона, включая ошибку, отмену, диагностику и проверку
MCP, закрыть все запущенные для него процессы. Внутри непрерывного прогона клиент
можно переиспользовать; после окончания этапа и перед ожиданием ответа пользователя
оставлять его запущенным нельзя, если пользователь явно не попросил обратное.

1. Перед запуском запомнить существующие процессы и сеансы, затем учитывать свои
   PID, профиль, базу и пути логов. Не определять принадлежность только по имени EXE.
2. Сохранить нужный отчёт. Штатно завершить свои клиенты 1С и Конфигураторы.
   Если агент запускал менеджер Vanessa и его TestClient, выполнить
   `./scripts/onec.ps1 va-mcp --stop`. Эта команда закрывает оба процесса;
   не применять её к менеджеру, который был запущен другим пользователем или задачей.
3. Завершить собственные разовые MCP-проверки и вспомогательные процессы.
   Постоянные MCP-серверы, которыми управляет приложение, и службы 1С/СУБД
   не относятся к процессам отдельного прогона и не останавливаются.
4. Проверить исчезновение своих PID и сеансов; для остановленного своего менеджера
   Vanessa проверить отсутствие его слушателя на порту из конфигурации.
   Сообщение команды «остановлен» само по себе не заменяет проверку.
   Если после завершения процесса остался свой сеанс, использовать
   [порядок закрытия сеансов](#sessions). Чужие сеансы не завершать.
5. При неудаче остановки сообщить, что именно осталось и почему. Не объявлять
   уборку завершённой. Общий `taskkill` всех процессов 1С недопустим.

<a id="frozen-main"></a>
## Замороженная типовая и кэш

Раннер собирает расширения вместе с основной конфигурацией; `test` начинается со сборки.
Его копия типовой — `1c/v8runner/main`, а `1c/config` предназначена для поиска.
Кэш заполняется успешной сборкой, а не выгрузкой. Первичная команда
`./scripts/onec.ps1 v8 build --source-set main` выполняет полную загрузку типовой:
применять её только на этапе осознанного развёртывания с проверенной совместимой
копией исходной демо-конфигурации. Старую выгрузку в другом формате туда не подставлять.

Перевыгрузка может недетерминированно менять макеты-диаграммы; раннер видит изменение
и пытается частично загрузить типовую на поддержке. Симптом — `Cannot restore configuration …
editing metadata object … is not allowed`. Вернуть проверенную замороженную копию,
а дальнейшую инициализацию согласовать с фактическим состоянием кэша и базы.
`designer-main.redb` для обхода ошибки расширения не удалять.

Кэш `1c/v8runner/build` не входит в `.dt`. После восстановления базы из снимка кэш может
не соответствовать базе. При необходимости полной сборки использовать `--full-rebuild`
в рамках восстановления; это не стандартное действие при каждой правке расширения.
`v8project.local.yaml` создаёт харнесс и сверяет со stand.json; переписывание кавычек
раннером не является причиной править подключение вручную.

<a id="runner-load"></a>
## Отказы загрузки раннера

На проверенной Windows-сборке раннер мог завершиться до Конфигуратора и продолжить
запуск Предприятия после ошибки загрузки. Поэтому код выхода процесса не заменяет
проверку `1c/v8runner/build/logs/platform/*-load.log`; обход реализован в `onec.py`.
Прямой exe раннера и его MCP-инструмент `test` обход не используют.

- «Неизвестная версия формата 2.21», `Caption` / `ShortCaption` — исправлять источник
  расширения по [правилу формата](../../onec-extension-xml/SKILL.md#format).
- «Ошибка XDTO … Synonym», «НачалоСвойства: ObjectPresentation» или «НачалоСвойства: Title» —
  убрать лишний `Synonym` у строки локализации, см.
  [правило представлений](../../onec-extension-xml/SKILL.md#presentation).
- Код выхода Конфигуратора 1 и пустой `1c/logs/load-extension.log` (0 байт либо только
  `EF BB BF`) не диагностика XML. Трёхбайтовая метка в этом логе — BOM самого `/Out`,
  её появление и обнуление не означает, что в исходниках не хватает BOM. Ждать текст
  лога до завершения процесса; параллельную загрузку не запускать: она затирает тот же файл.
- «Ошибка чтения файла-списка загружаемых файлов» — `v8 test yaxunit` через харнесс
  один раз повторяет полную загрузку только расширения из `build-NN-<Имя>-load.log`.
  Кэш остальных расширений и типовой не сбрасывается. После полной загрузки проверить
  [флаги](#flags).

<a id="module-check"></a>
## Проверка модулей

Использовать MCP `check_syntax_designer_modules` с `allExtensions=true`,
`extendedModulesCheck=true`, `server=true`, `thinClient=true`. Изолированная проверка
тестового расширения не видит `ЮТест`; все расширения учитывают зависимость YAxUnit.
Если тест не видит объект другого расширения, исправить
[размещение тестового модуля](checks.md#server).

Раннер возвращал ошибку даже при `No syntax errors found!` в логе платформы. Судить
по свежему логу, путь к которому есть в ответе. Реальные диагностики не игнорировать;
известное ограничение стороннего помощника — [ниже](#va-diagnostics).

При диагностике всех расширений разделять записи свежего лога по имени расширения.
В прогоне 08.10.2026 108 диагностик относились к `ПримальпОбувь` и `VAExtension`,
а к новой обработке замечаний не было. Это историческое наблюдение, не допустимый
постоянный список: каждый раз проверять текущий лог, сообщать чужие диагностики
отдельно и не называть общую проверку чистой. Чужие расширения ради зелёного отчёта
не отключать и не исправлять вне задачи.

<a id="external-test-stall"></a>
### Внешняя обработка не открывается из серверного YAxUnit

При явной ошибке «Установлен безопасный режим. Выполнение операции запрещено»
сначала применить [снятие флагов](#flags) только к тестовому расширению и повторить
целевой прогон. Загрузка раннером может включить флаги снова; проверять фактическое
состояние после полной загрузки, включая автоматический обход частичной загрузки.

В прогоне EPF 08.10.2026 после снятия флагов прямой вызов
`ВнешниеОбработки.Создать(...)` завис без результата; точная причина не установлена.
При повторении этого симптома не запускать ещё один Конфигуратор рядом с зависшим
клиентом: сохранить свежий `runner.log`, завершить свой клиент и его остаточный сеанс
по [порядку уборки](#run-cleanup). Проверенный путь продолжения — серверные тесты
синхронизированной копии и отдельный UI-прогон самого EPF по
[методике](checks.md#external-epf). Этот обход не заменяет проверку поставляемого файла.

<a id="reports"></a>
## Запуск тестов и достоверность отчёта

YAxUnit на проверенной Windows-сборке раннера получал некорректно переданный `/C`:
тонкий клиент просто открывал УТ. Харнесс сам собирает расширения и передаёт `/C`
и `RunUnitTests=<config.json>` разными аргументами. Запускать серверные тесты через
[команду харнеса](#commands).

YAxUnit должен оставить свежий `1c/v8runner/build/temp/yaxunit/manual/report.xml`.
Харнесс удаляет старый отчёт перед запуском и требует ненулевое число `testcase`.
Для отдельного каталога параметров и отчётов Windows-прогона задать
`ONEC_YAXUNIT_RUN_DIR=1c/tmp/<уникальное-имя>` в окружении команды. Путь должен
находиться в `1c/tmp` проекта; харнесс печатает полный путь. Без переменной используется
прежний `manual`. Этот параметр защищает файлы обмена от перезаписи другим чатом,
но не отменяет последовательный запуск сборок и тестов.
Пустой отчёт, `failure`, `error` и `skipped` — не успех. Проверять их на всех
уровнях jUnit, включая наборы тестов и обработчики очистки `ПослеКаждогоТеста` /
`ПослеВсехТестов`, даже при ненулевом числе выполненных тестов. Прямой раннер мог удалить
свой каталог после теста; харнесс сохраняет указанный отчёт и печатает число тестов.

Vanessa создаёт отдельный каталог `1c/logs/vanessa/run-*`: сохранить его `junit.xml`,
`status.txt` и `steps.log`. Успех требует выполненных сценариев, отсутствия
`failure/error/skipped` и статуса `0`. Возврат процесса с кодом 0 сам по себе недостаточен.

При программном захвате stdout/stderr CLI учитывает, что `StringIO` не имеет
`reconfigure`; UTF-8 на обычной Windows-консоли сохраняется.

<a id="vanessa"></a>
## Vanessa и интерактивный MCP

`va` использует пустую файловую базу `1c/v8runner/va-manager`. Прямой `v8 test va`
запускал менеджер в УТ и зависал на стартовых окнах без лога.
Сценарий подключать к профилю «УТ» шагом
`Дано я подключаю TestClient "УТ" логин "Администратор" пароль ""`.
Без явного подключения Vanessa может выбрать своего клиента в пустой базе.

Для пошаговой работы: `manage_test_client` (`connect`, профиль «УТ»), затем
`open_feature_file` и `execute_feature_step` с явным `filePath`.
Без `filePath` возникало «Не удалось активировать вкладку файла».
После первого открытия feature в свежем менеджере ошибка дерева файла `<>` устраняется
повторным `open_feature_file`, затем исполнением шага.
Пути на Windows должны вести в проект; `/run/host` относится к Linux-контейнеру.
Приёмы работы с формами и скриншотами — [методика UI](checks.md#ui).

`manage_test_client` подключается, но не запускает клиент. Если он закрыт или загружено
расширение, использовать `va-mcp --restart-client`, затем повторное подключение.
Пакетный `va` и интерактивный MCP используют раздельные диапазоны портов; при отказе
подключения сверить порт в `steps.log` с `va_client` в харнессе.

<a id="va-unresponsive"></a>
### MCP Vanessa перестал отвечать после ошибки сценария

Таймаут `run_scenario` сам по себе не означает отказ сценария: проверить
`get_test_results` и свежий журнал менеджера. Если MCP отвечает, прочитать детали
модального окна, закрыть его через инструменты Vanessa и исправить первичную ошибку.

Если повторно не отвечают и команды чтения, не накапливать параллельные запросы.
Для своего менеджера выполнить `va-mcp --stop`, проверить остановку и оставшиеся
сеансы по [порядку уборки](#run-cleanup), затем `va-mcp` и подключить профиль «УТ».
Если штатная остановка также зависла, допустимо завершить только заранее учтённые
свои PID, сверив их командные строки и пути логов; затем убрать свои остаточные сеансы.
Не делать вывод о причине зависания лишь по наличию открытого порта.

После перезапуска проверенный путь — `open_feature_file` и `execute_feature_step`
с явными `filePath` и реальным номером строки. Законченный сценарий можно выполнить
пакетной командой `va --path <конкретный feature>` после остановки своего MCP-менеджера.
На этом стенде такой порядок завершил прогон после зависания интерактивного запуска.
После пересборки EPF использовать свежий клиент, чтобы исключить ранее подключённую версию.

<a id="startup-dialogs"></a>
### Первые окна и доступность сервера

MCP Vanessa — сеанс менеджера, а не процесс, запускаемый клиентом Codex/Cursor.
Пока сервер не поднят командой `va-mcp`, инструментов нет. Адрес брать из
сгенерированного MCP-конфига, не прописывать второй адрес вручную.

Первый старт останавливается на «Мастер настройки интерактивной справки» — нажать
«Продолжить», без скачивания озвучки и уроков. Если тестовый клиент показывает
«Информационная база была перемещена», выбрать «Информационная база перемещена».
«Это копия информационной базы» меняет идентификатор базы. После готовности сервера
переподключить MCP `vanessa` в Cursor. Остановка — `va-mcp --stop` через харнесс.

<a id="mcp-ready"></a>
### Порт открыт, но команда даёт Tool not found

Порт открывается раньше регистрации инструментов. На Windows запуск `va-mcp` через
`subprocess.Popen` сохраняет аргументы с пробелами и сообщает «готов» только после
успешного read-only `manage_test_client_profiles/get_list`. Раньше `os.execvpe`
терял такие аргументы. Таймауты проверки заданы в `wait_va_mcp_ready` в `onec.py`;
при отказе команда указывает `1c/logs/va-mcp/manager.log`.

Если доступны только `infobase_info`, сверить закреплённую обработку: скачанная
раннером 05.10.2026 сборка не содержала MCP, поэтому применяется scripts/vanessa.json.
В проверенном комплекте `get_vanessa_automation_state` остаётся недоступным;
готовность подтверждать списком профилей и фактическими командами.

<a id="manager-security"></a>
### Предупреждение безопасности или ошибка конструктора Файл

`onec.py` дописывает `DisableUnsafeActionProtection=.*va-manager.*` в общий `conf.cfg`,
на который указывает `ConfLocation` из `bin/conf/conf.cfg`. Общий Windows-файл — UTF-16;
кодировку сохранять, строку во второй файл не копировать. Запись в каталог платформы
требует прав администратора.

Расширение `client_mcp` в базе-менеджере тоже требует снятия флагов. При включённых
флагах чтение формы работает, но открытие feature, шаги и скриншоты падают на `Файл`.
`va-mcp` снимает флаги после загрузки и только потом ставит `client_mcp.ready`.
Если флаги остались, на остановленном менеджере убрать только эту отметку и снова
запустить менеджер харнессом.

<a id="va-extension"></a>
## Служебное чтение данных MCP

`get_table_data` требует VAExtension в рабочей базе, отдельно от `client_mcp` менеджера.
Отсутствующая форма `VAExtension_ПолучениеДанныхИзБазы` — повод проверить установку
и свежесть клиента; это не доказательство отсутствия запрашиваемого объекта.

Закрыть свой TestClient, проверить `preflight`, выполнить
`./scripts/onec.ps1 download-va-extension`. Версию, SHA-256 и путь брать из вывода команды
и scripts/vanessa.json. Загрузить полученный CFE как `VAExtension` по
[процедуре загрузки](#extension-lifecycle), затем подключить свежий клиент.

Харнесс проверяет SHA-256 скачанного файла и существующего кэша. При несовпадении
сохранить именно указанный файл под другим именем и повторить скачивание.
Не использовать повреждённый кэш. Если помощник недоступен, остаётся
[чтение через список и форму](checks.md#ui).

<a id="va-diagnostics"></a>
### Диагностики официального VAExtension

В архивном прогоне 06.10.2026 (см. [архив тренировок](#repository-cleanup)) общая extended-проверка дала пять диагностик
VAExtension: `sysForm:AllFunctionsForm`, `sysForm:DesktopCustomization` и три обращения
к `УниверсальныйОтчет`. Собственные модули были без диагностик. Чтение данных MCP прошло,
а дополнительные формы помощника не проверялись. Общую проверку чистой не называть;
диагностики стороннего расширения отделять от собственных, не отключая проверку.
Версии, точный лог и границы этого наблюдения зафиксированы в журнале.

<a id="legacy"></a>
## Прочие диагностические случаи

- `bsl-platform` на первом старте может не успеть прочитать справку до таймаута MCP.
  Повторить подключение и проверить путь к установленной справке в сгенерированном
  конфиге. Java и пути инструментов брать из фактического окружения, не из старого конфига.
- `Unable to initialize GTK+`, exit 255 без дисплея, D-Bus, colord и DRI3 относятся
  к прежнему Linux-контейнеру. На текущем Windows-стенде виртуальный дисплей не нужен.
  Шум контейнерного окружения сам по себе не заменяет статус, свежий отчёт и лог.

<a id="repository-cleanup"></a>
## Размещение и очистка служебных файлов

- `1c/extensions`, `1c/vanessa/features`, `.agents/skills`, `scripts` — поддерживаемые
  исходники, сценарии и инструменты. Незакоммиченный файл здесь не означает мусор.
- `docs/reports` и датированные журналы — сохранённые свидетельства проверок.
  Их исторические параметры не заменяют `stand.json`; красные прогоны объясняют
  исправления и могут быть нужны вместе с зелёными.
- `1c/tmp` — временный обмен и диагностические копии; `1c/logs` — журналы запусков;
  `1c/vanessa/features/png` — автоматически снятые изображения ошибок.
  Перед очисткой закончить использующий их прогон, сохранить нужные отчёты и
  проверить обращения из сценариев. Сам каталог `1c/tmp` оставить для обмена.
- `.local` — локальная диагностика, в том числе возможные файловые базы; `build/tools`
  — инструменты; `1c/config` — выгрузка для поиска; `1c/v8runner` — замороженная
  типовая, менеджер Vanessa и кэш. Не считать эти каталоги одноразовым мусором.
- `1c/artefacts`, `artifacts` и старый `1c/artifacts` — локальные поставки и архивы.
  Новые поставки размещать в `1c/artefacts`; существующие не переносить без обновления
  скриптов и ссылок. Срок хранения брать из манифеста конкретной поставки.

Ротированные `mcp-server.log.*` можно убирать после завершения записи. Активный
`mcp-server.log` не удалять. Не применять общий `git clean -fdx`: он захватывает
локальные настройки, выгрузку и инструменты. Удалять только явно выбранные пути
внутри проекта, проверив их абсолютные адреса и отсутствие ссылок за его пределы.
При сомнении сохранить диагностические материалы в локальный ZIP с перечнем
файлов и SHA-256; архив не добавлять в Git и не объявлять проверенной поставкой.

### YAxUnit 25.12 и УТ без обработчика отображения ошибок

Проверка применимости обнаружила отсутствующие `ОбработкаОтображенияОшибки` и
`ErrorDisplayProcessing` в обоих модулях приложения. Для этой УТ выгрузить YAXUNIT
через `dump-extension`, выполнить `scripts/prepare_yaxunit_ut.py <каталог>` и загрузить
исправленную выгрузку через `load-extension --apply`. Скрипт проверяет версию и отсутствие
обработчиков в типовой, убирает только четыре аннотации перехвата и устанавливает
совместимость из `stand.json`. Процедуры сохраняются; автоматического перехвата глобальных
ошибок через отсутствующие события нет. Повторная установка оригинального CFE вернёт
аннотации: адаптацию и проверку применимости потребуется повторить.

# Research: Обмен «Счет на оплату покупателю» → «Заказ»

Дата: 2026-11-08. Все решения опираются на проверенные механизмы: `bsp/src/extensions/СервиснаяШинаПредприятия/` (ВК librdkafka), `ЭкспортТоваровВШину/` (ЭТШ_ — продюсер), `uf_demo/src/extensions/ИмпортТоваровИзШины/` (ИТШ_ — консьюмер). NEEDS CLARIFICATION в плане не осталось — все открытые вопросы разрешены уточнениями спеки (9 ответов в `spec.md#Clarifications`).

## R-1. Размещение и состав расширений

**Decision**: два новых расширения — `ЭкспортСчетовВШину` (`ЭСВ_`) в `bsp`, `ИмпортСчетовИзШины` (`ИСШ_`) в `uf_demo`; оба с собственным `NamePrefix`. Обёртка ВК приёмника — локальный модуль `ИСШ_Шина`, копия паттерна `ИТШ_Шина`.

**Rationale**: конституция I–II (Extension-First, самодостаточность): `/CheckConfig` компилирует каждое расширение изолированно — вызов `ИТШ_Шина` из `ИСШ_ЗагрузкаСчетов` дал бы «Переменная не определена». Прецеденты ЭТШ/ИТШ показывают одну обработку с формой на сторону обмена.

**Alternatives considered**: доработка ЭТШ/ИТШ — запрещена конституцией IV (существующие модули не изменяются) и сломала бы работающий обмен товарами; один общий обработчик — невозможен (разные конфигурации без связи).

## R-2. Подключение внешней компоненты

**Decision**: `ЭСВ_` подключает ВК из бинарных макетов СШП (`ОбщийМакет.librdkafka_win32/win64/linux32/linux64`) — по прецеденту ЭТШ, включая fallback «компонента уже подключена в сеансе» (внешнее соединение). `ИСШ_` использует собственные копии макетов `ИТШ_librdkafka_*`, переименованные в `ИСШ_librdkafka_*` с новыми UUID (прецедент ИТШ — в uf_demo нет СШП).

**Rationale**: бинарные макеты — не модули, правило изоляции их не запрещает; оба прецедента уже проверены в обеих конфигурациях. Дублирование 4 бинарников в bsp неоправданно (DRY), а в uf_demo без СШП копия обязательна.

**Alternatives considered**: ссылка ИСШ на макеты ИТШ — нарушает самодостаточность; использование модулей СШП (`СШП_Отправитель/Получатель`) — запрещено (правило 13 AGENTS.md, изолированная компиляция).

## R-3. API внешней компоненты (подтверждено кодом)

**Decision**: продюсер — `New("AddIn.librdkafka.KafkaProducer")`, `Initialize(Адрес, Топик, -1)`, `SetJSONMessageList(JSON-массив)`, `Produce()`, `IsDelivered()`, `GetJSONDeliveryReport()`; консьюмер — `New("AddIn.librdkafka.KafkaConsumer")`, `SetGlobalConf("enable.auto.commit","false")`, `SetTopicConf("auto.offset.reset","earliest")`, `Initialize(Адрес, Группа)`, `ClearSubscribeList()`, `AddTopicToSubscribeList(Топик)`, `Subscribe()`, `ConsumePool(5000, 1000, 1)`, `ReceiveJSONMessages(Ложь)`, `GetMessagePoolLength()`, `ClearMessagePool()`, `Commit()`. Сообщение: `{Headers: [], Key: строка, Value: строка JSON}`. Таймаут «Local: Timed out» и полный пул — не ошибки; при ошибке порции офсеты не коммитятся.

**Rationale**: это фактический API работающих ЭТШ/ИТШ (см. `ЭТШ_ЭкспортТоваров`, `ИТШ_Шина`, `ИТШ_ЗагрузкаТоваров`) — перепроверка не требуется.

## R-4. Формат сообщения счёта и топик

**Decision**: топик по умолчанию `invoices`, группа по умолчанию `uf-demo-invoices` (адрес `localhost:9092`); оба вводятся в форме. Ключ сообщения — `Номер|ДатаISO` (детерминированная идентичность, партиционирование по счёту). Value — JSON:

```json
{
  "Номер": "ТД00-000123", "Дата": "2026-11-08T10:00:00",
  "Организация": {"Наименование": "..."},
  "Покупатель": {"Наименование": "..."},
  "Валюта": {"Код": "643", "Наименование": "RUB"},
  "Сумма": 12345.67,
  "Товары": [{"Артикул": "...", "Наименование": "...", "Штрихкод": "...", "Количество": 2, "Цена": 100, "Сумма": 200}]
}
```

Дата — строка ISO, при чтении парсится `XMLЗначение(Тип("Дата"), ...)`. Количество в JSON — число (источник хранит 15,3; приёмник усекает до целого — Цел() с предупреждением в протоколе).

**Rationale**: структура повторяет формат ЭТШ (`Headers/Key/Value`), дататаймы в JSON 1С сериализуются в ISO штатно; ключ из пары «номер+дата» согласован со спекой FR-007 (идентификация заказа).

**Alternatives considered**: GUID счёта в ключе — не воспроизводим в приёмнике (справочники не связаны); ключ только номер — неоднозначен при `NumberPeriodicity=Year`.

## R-5. Сопоставление справочников и обрезки

**Decision**: товары — Артикул (обрезка до 15 при поиске, конвенция ИТШ: товары могли быть созданы ИТШ с обрезанными артикулами) → Штрихкод (до 20) → Наименование (**строго полное**, без обрезки — clarify Q5); контрагент/организация — точное полное наименование; валюта — Код → Наименование. Номер счёта обрезается до 9 символов (длина номера приёмника) с предупреждением в протоколе. Если артикул/штрихкод длиннее полей приёмника (15/20) — шаг поиска считается непрошедшим, идём дальше по цепочке.

**Rationale**: длинные наименования физически не существуют в полях приёмника (30/25/50), поэтому запрос с полным значением корректно вернёт «не найдено» без специальной обработки; обрезка артикула/штрихкода необходима для совместимости с созданными ИТШ товарами (спека уточняет строгость только для наименования). Конвенция обрезки ИТШ подтверждена кодом (`СократитьСтроку`).

**Alternatives considered**: обрезка наименований для поиска — отклонена пользователем (ложные совпадения двух разных элементов с общим префиксом).

## R-6. Сверка: отчёт в БСП через HTTP-сервис приёмника (изменено 2026-11-09)

**Decision** (по явному указанию пользователя): сверка выполняется в базе источника по образцу существующей сверки товаров (`СверкаСправочников`, СС_): HTTP-сервис приёмника `ИТШ_Товары` расширяется шаблоном `Заказы` (`/v1/orders`), возвращающим заказы приёмника (не помеченные на удаление) в JSON — шапка (Номер, Дата, Организация.Наименование, Покупатель.Наименование, Валюта.Код, Сумма) и строки (Товар.Наименование, Товар.Артикул, Количество, Цена, Сумма). В источнике модуль `СС_ЗагрузкаЗаказов` читает HTTP-ответ в регистр `СС_СостояниеЗаказовПриемника` (плоский, запись на строку заказа, НомерСтроки=0 для заказа без строк; полная перезапись среза), обработка `СС_ОбновлениеСрезаЗаказов` — кнопка «Загрузить срез», отчёт СКД `СС_СверкаЗаказов` — ПОЛНОЕ СОЕДИНЕНИЕ счетов источника (с ТЧ) со срезом по ключу Номер (обрезанный до 9) + Дата + НомерСтроки, статусы: Совпадает / Расходится / Нет в приёмнике / Нет в источнике / Счёт помечен на удаление. Публикация uf-demo-test на Apache настраивается и проверяется в рамках фичи.

**Rationale**: повторяет проверенную архитектуру товарной сверки (СС_СверкаТоваров: HTTP → регистр → отчёт СКД), пользователь прямо указал этот путь; в приёмнике не нужен ни эталонный справочник, ни обработка сверки — расширение ИСШ_ остаётся только механизмом загрузки. Сравнение строк — по наименованию товара приёмника против наименования номенклатуры источника (в демо-данных совпадают; товар, найденный по артикулу, в демо имеет то же наименование).

**Alternatives considered**: эталонный справочник в приёмнике (первоначальный R-6) — отклонён пользователем; перечитывание топика при сверке — ненадёжно (ретеншн, офсеты).

**Следствия**: удалены из плана ИСШ_СчетаОбмена, ИСШ_СверкаЗаказов (модуль и обработка); Т012 больше не пишет эталон; добавлены задачи T020–T022 (HTTP-шаблон, СС_ объекты, отчёт+Apache). Правка существующего ИТШ_ — исключение из правила «существующие модули не изменяются» по явному указанию пользователя (новый шаблон и новый обработчик; существующий код товаров не трогается).

## R-7. Запись заказа и транзакции

**Decision**: создание/обновление заказа — в транзакции: поиск по «номер + дата» (с обрезанным номером), при создании — номер (обрезанный), дата счёта, организация/покупатель/валюта (найденные), валюта в `Валюта`, сумма шапки = сумма строк сообщения, склад — первый непомеченный склад с `НеИспользовать = Ложь` (нет склада — протокол-ошибка), состояние `СостояниеЗаказа.Открыт`, `Товары` — полная замена строк данными сообщения (сортировка как в счёте). Проведение не выполняется (`Записать()` без `Провести()`), заказ помеченного на удаление — пропуск (clarify Q5 раунда 1), атомарный пропуск при ненайденных (clarify Q6 раунда 2). Проверка разрядности цены/суммы (10,2) и количества (10,0) до записи; превышение — протокол-ошибка.

**Rationale**: полная замена ТЧ проще дифф-сопоставления и даёт тот же результат «приведения в соответствие» (конституция IV — KISS); транзакция гарантирует атомарность FR-008; заполнение состояния явно, т.к. `FillValue` применим только к заполняемым из формы объектам.

## R-8. Протокол и сообщения пользователю

**Decision**: модули возвращают структуру итогов (Прочитано, Создано, Обновлено, Пропущено, Ошибок + МассивПротокола — строки «счёт: сообщение»); формы выводят итоги через `Сообщить()` (правило проекта для клиентского кода форм). Журнал регистрации: ошибки — `Ошибка`, ключевые итоги — `Информация`, имя журнала `ИмпортСчетовИзШины.*` / `ЭкспортСчетовВШину.*` (прецедент ИТШ).

**Rationale**: ИТШ уже использует возврат структуры итогов + журнал регистрации; `Сообщить()` — конвенция проекта (правило 13 AGENTS.md).

## R-9. Vanessa-фичи и скриншоты для PDF

**Decision**: фичи `bsp/Vanessa/features/scheta/`: экспорт (`scheta-export.feature`, база InfoBase22, прогон `va.ps1`), данные источника и подготовка (`scheta-source-data.feature`), импорт/повтор/сверка (`scheta-import.feature`, база uf-demo-test, прогон `va-nouser.ps1`). Сквозная последовательность: 1 экспорт из InfoBase22 → загрузка в uf-demo-test (проверки: заказы, «ошибок: 0») → повтор (количество заказов не меняется) → сверка (расхождений нет). Скриншоты для PDF — шагами снимка окна Vanessa (прецедент `pko-pechat-shot.feature`), каталог выгрузки скриншотов — временный; PDF собирается скриптом из скриншотов с подписями на этапе реализации.

**Rationale**: соответствие существующей организации фич и раннеров (AGENTS.md); недетерминизм по количеству сообщений в топике (офсеты группы в брокере) учтён — проверяются `Ошибок = 0` и содержимое, как в goods-фичах.

## R-10. Порядок внедрения и проверки

**Decision**: 1) расширение ЭСВ_ (XML-исходники по шаблону ЭТШ) → загрузка в InfoBase22 → `/CheckConfig`; 2) расширение ИСШ_ (XML-исходники по шаблону ИТШ + копии бинарных макетов) → загрузка в uf-demo-test → `/CheckConfig` → снять SafeMode/Защиту (GUI, конституция — раздел «Технические ограничения»); 3) Vanessa-фичи и прогоны; 4) сборка PDF. Состав объектов расширений создаётся файлами выгрузки XML и загружается Конфигуратором (как предыдущие расширения проекта).

**Rationale**: каждая сторона проверяется изолированно до сквозного прогона; безопасность ВК снимается один раз вручную (ibcmd отсутствует — только GUI).
